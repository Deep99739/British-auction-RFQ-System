## Table decisions

### `auctions`

Stores configuration and the mutable effective close.

Important constraints:

- Start is before initial close.
- Initial close is not after current close.
- Current close is never after forced close.
- X and Y are positive.
- Trigger type is one of the three supported modes.

Keeping both `initial_close_at` and `current_close_at` makes extension usage visible without reconstructing it from logs.

### `suppliers`

Supplier names are matched by a generated normalized value in the current
prototype. A production identity system would provide a stable organization ID
and remove name-based identity from bid commands.

### `bids`

Bids are immutable. A supplier revision creates another row.

`total_amount` is generated by PostgreSQL from the three required charge components. This prevents the client-provided total from disagreeing with stored components.

The unique `(auction_id, idempotency_key)` constraint makes a retried command safe.

### `activity_log`

Records human-readable history plus structured JSON metadata. It is append-only and supports audit display without recomputing historical reasons from current configuration.

## Current-ranking query

1. Partition bids by supplier.
2. Select the newest bid for each supplier.
3. Sort those bids by total ascending.
4. Break equal totals by earlier submission, then bid ID.
5. Assign `ROW_NUMBER()` as L1, L2, L3, and so on.

## Indexes

- `auctions(current_close_at)` supports deadline and closure scans.
- `bids(auction_id, supplier_id, submitted_at DESC, id DESC)` supports latest-bid selection.
- `bids(auction_id, total_amount, submitted_at, id)` supports ranking.
- `activity_log(auction_id, created_at DESC, id DESC)` supports the auction timeline.

Indexes are intentionally tied to current queries rather than added speculatively.
